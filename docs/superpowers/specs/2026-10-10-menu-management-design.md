# แบบขยายระบบจัดการเมนู

สถานะ: เจ้าของยืนยันให้เริ่มพัฒนาในแชตนี้แล้ว โดยแก้ชื่อเครื่องเป็น “ฟักทองเชื่อม”

## เป้าหมายและสิ่งที่ยืนยันแล้ว

เจ้าของร้านจัดลำดับ เพิ่ม ลบ และแก้เมนูพร้อมตัวเลือกและข้อความที่ลูกค้าเห็นได้จากหน้า “จัดการเมนู” โดยไม่ต้องแก้โค้ด บิลเดิม ชื่อ/ราคาในบิล สิทธิ์พนักงาน QR และการป้องกันออเดอร์ซ้ำต้องคงอยู่ ใช้หน้าตาเดิมของร้าน: ภาษาไทย ตัวหนังสือใหญ่ ปุ่มกดง่ายบน iPhone

เจ้าของยืนยันว่า “มันเชื่อม” ที่ซ้ำให้เหลือรายการเดียว ถั่วลิสงเลือกไว้ให้แต่ลูกค้าเอาออกได้ และไม่นับรวมเครื่อง 3/4 อย่าง

ตรวจฐานเริ่มต้น: `main` ที่ `b279bbc` ตรงกับ remote, working tree สะอาด, `pnpm check` ผ่าน 49 tests รวม typecheck/lint/build/HTML ส่วน PR #1 เป็นงาน security/CI แยกที่ยังไม่ได้รวม

อ่าน public menu จริงพบกระเพรา 2 เมนูที่ Owner เพิ่มเอง: หมูสับ 55 บาท และหมูกรอบ 65 บาท ทั้งคู่ยังไม่มีตัวเลือกเพิ่ม ไอศกรีมเล็ก 30/ใหญ่ 40 บาทยังไม่มีเครื่อง ข้อมูลนี้เป็นการอ่านเท่านั้น

## แนวทางที่เสนอ

ใช้หน้าจัดการเมนูเดิม แล้วเพิ่มการตั้งค่าเฉพาะแต่ละเมนู เป็นแนวทางแนะนำเพราะร้านแก้ได้เองและการแก้เพิ่มพิเศษของจานหนึ่งไม่กระทบอีกจาน

ทางเลือกที่แคบกว่าคือเพิ่มเฉพาะไข่ดาวกับเครื่องไอศกรีม แต่ร้านยังแก้ข้อความและตัวเลือกเองไม่ได้ ส่วนการทำตัวสร้างหน้าจออิสระทั้งระบบจะซับซ้อนเกินงานหน้าร้านรอบนี้ จึงจำกัดการแก้ข้อความไว้ที่หน้าลูกค้าปรับรายละเอียดเมนู

## หน้ารวมเมนู

- ค้นหาชื่อและกรองตามหมวด
- เพิ่มเมนูใหม่ และแก้เมนูเดิมด้วยฟอร์มเดียวกัน
- ปุ่มเลื่อนขึ้น/ลงจัดลำดับเมนูภายในหมวด ใช้ได้ด้วยการแตะ ไม่ต้องลากอย่างเดียว ลำดับเดียวกันแสดงในหน้าลูกค้าและ POS
- แยก “ปิดขายชั่วคราว” ออกจาก “ลบเมนู” การลบนำเมนูออกจากหน้าสั่งอาหาร แต่ยังอยู่ในรายการ “เมนูที่ลบ” ของ Owner และกู้คืนได้
- ไม่ลบข้อมูลอ้างอิงของบิลเก่า พนักงานทั่วไปไม่มีสิทธิ์แก้รายการเมนู

## ฟอร์มเพิ่ม/แก้เมนู

แบ่งเป็นส่วนที่อ่านง่าย และมีปุ่มดูตัวอย่างหน้าที่ลูกค้าเห็นก่อนบันทึก:

1. ข้อมูลหลัก: ชื่อ หมวดที่มีอยู่ คำอธิบาย หน่วยขาย และเปิด/ปิดขาย
2. แบบ/ขนาดและราคา: แก้หัวข้อ “ขนาดอาหาร” เป็นข้อความของเมนูนั้น เช่น “ขนาดไอศกรีม” หรือ “เลือกรูปแบบ”; เพิ่ม/แก้/นำแบบออก เรียงลำดับ และตั้งราคาแต่ละแบบ
3. ตัวเลือก/เพิ่มพิเศษ: เพิ่ม/แก้/นำกลุ่มและรายการออก เปลี่ยนชื่อ/ราคา เรียงลำดับ เปิด/ปิดตัวเลือก และเลือกค่าเริ่มต้นได้ โดยการแก้มีผลเฉพาะเมนูนั้น
4. กติกาตัวเลือก: กำหนดขั้นต่ำ/สูงสุดของแต่ละกลุ่ม รวมถึงจำนวนที่ต่างกันตามแบบ เช่น ไอศกรีมเล็ก 3/ใหญ่ 4 อย่าง จำนวนที่เลือกได้บนหน้าลูกค้าแสดงจากกติกาจริง
5. ข้อความหน้าลูกค้า: คำแนะนำใต้ชื่อเมนู หัวข้อแบบ/ขนาด ชื่อกลุ่มตัวเลือก หัวข้อหมายเหตุ และข้อความตัวอย่างในช่องหมายเหตุ รวมถึงรายการหมายเหตุสำเร็จรูป

เก็บข้อความเป็นข้อความธรรมดา ไม่รับ HTML/สคริปต์ ช่องที่ไม่กำหนดใช้ข้อความมาตรฐานเดิม เมนูเดิมยังแสดงได้ระหว่างอัปเดต แสดงข้อผิดพลาดชัดเจนและเก็บร่างไว้เมื่อบันทึกไม่สำเร็จ กรณีข้อมูลถูกแก้จากอีกเครื่องให้แจ้งและโหลดข้อมูลใหม่แทนการทับโดยไม่รู้ตัว

รอบนี้ยังไม่เพิ่มระบบรูปภาพ เสียงพูด สต็อก สูตรอาหาร หรือการแก้ข้อความของทั้งเว็บนอกหน้าปรับรายละเอียดเมนู

## รายการที่แก้ให้ร้านในรอบนี้

### ข้าวผัดกระเพรา

เพิ่มกลุ่ม “เพิ่มพิเศษ” ให้ทั้งข้าวผัดกระเพราหมูสับและหมูกรอบ:

- “เพิ่มไข่ดาว” ราคาเพิ่ม 10 บาท เลือกได้ 0–1 ฟองต่อจาน ค่าเริ่มต้นไม่เลือก
- เลือกแล้วเอาออกได้ และแสดงราคาบนปุ่ม/ยอดตะกร้าและรายละเอียดครัว
- ราคาฐานเดิม 55/65 บาทไม่เปลี่ยน

ใช้รหัสเมนูที่ตรวจพบจริงเพื่อไม่สร้างเมนูกระเพราซ้ำ ไม่เปลี่ยนตัวเลือกของเมนูข้าวอื่นโดยอัตโนมัติ

### ไอศกรีมมหาชัย

- หัวข้อ “ขนาดไอศกรีม”; เล็ก 30 บาท ใหญ่ 40 บาท
- กลุ่ม “เลือกเครื่อง”: เล็กเลือกได้ 0–3 อย่าง ใหญ่ 0–4 อย่าง แต่ละรายการเลือกได้ครั้งเดียว ไม่มีค่าเพิ่ม
- เครื่อง: ถั่วทอง, ฟักทองเชื่อม, มันเชื่อม, ลูกชิด, สับปะรดเชื่อม
- กลุ่มถั่วลิสงแยกต่างหาก: “ถั่วลิสง (ใส่ให้อยู่แล้ว)” ฟรี เลือกไว้เริ่มต้น เอาออกได้ และไม่นับโควตาเครื่อง
- เปลี่ยนจากใหญ่ที่เลือก 4 อย่างเป็นเล็ก: เก็บตัวเลือกไว้และแจ้งให้ลดเหลือไม่เกิน 3 อย่างก่อนเพิ่มลงตะกร้า ไม่แอบตัดตัวเลือกแทนลูกค้า
- ตะกร้าและใบครัวแสดงเครื่องที่ลูกค้าเลือก และแสดง “ไม่ใส่ถั่วลิสง” เมื่อเอาถั่วลิสงออก เพื่อให้ครัวแยกจากค่าเริ่มต้นได้

## โครงสร้างและการรักษาข้อมูล

คง React/Vite, Supabase, Node demo และ HTML preview ใช้ migration ใหม่เท่านั้น ไม่แก้ SQL ที่เคยลงแล้ว

- เพิ่มลำดับ เมตาดาทาข้อความ และ revision ของเมนู
- เพิ่มลำดับและชื่อที่ใช้เฉพาะเมนูบนการเชื่อมกลุ่ม/ตัวเลือก พร้อมกติกาต่อแบบ แก้ชื่อ/ราคาหรือเอาตัวเลือกออกจากเมนูหนึ่งโดยไม่แก้กลุ่มที่เมนูอื่นใช้อยู่
- คงรหัสและแถวที่บิลเก่าอ้างอิง เมนู/แบบที่ถูกลบใช้สถานะเลิกขาย กลุ่ม/ตัวเลือกที่ปลดออกยังมีข้อมูลเดิมใน snapshot ของบิล
- แยกการอ่าน catalog สำหรับ Owner (รวมเมนูที่ลบและข้อมูลตั้งค่า) จาก catalog สาธารณะ ใช้บัญชี/สิทธิ์เดิม
- เพิ่ม RPC และเส้นทาง staff API สำหรับบันทึกเมนูครบชุด จัดลำดับ ลบ/กู้คืน ตรวจ Owner ทั้ง handler และฐานข้อมูล บันทึกการแก้ครบชุดใน transaction
- ใช้ expected revision ป้องกันการทับจากสองเครื่อง และรหัสคำขอคงเดิมสำหรับ retry การบันทึก/เรียง/ลบ กติกาเมนูเดิมและ client เก่าต้องไม่หลบการตรวจสิทธิ์หรือทำให้ retry สร้างรายการซ้ำ
- เซิร์ฟเวอร์คำนวณราคาและตรวจจำนวนเครื่องตามแบบอีกครั้ง ไม่เชื่อราคาหรือจำนวนจากหน้าเว็บ บิลเดิมที่ส่งสำเร็จแล้วต้อง retry กลับมาเป็นบิลเดิม แม้เมนูถูกแก้/ลบภายหลัง
- Node demo และ HTML mock รองรับข้อมูล/พฤติกรรมเดียวกัน โดยอัปเกรดข้อมูลท้องถิ่นแบบไม่ทับเมนู/ราคาที่ Owner แก้ไว้

จะปรับ `src/menu-management.ts`, เพิ่มส่วนประกอบฟอร์มแยกใน `src/staff/`, ต่อ `src/pages/MenuEditor.tsx`, หน้าตัวเลือกใน `Ordering.tsx`, domain/API adapters, Node/HTML adapters และเพิ่ม SQL/RPC ที่เกี่ยวข้อง ไม่มีการแก้การรับเงิน/สถานะครัว/QR ในงานนี้

## เกณฑ์ตรวจรับและเผยแพร่

- Owner เพิ่ม/แก้/เรียง/ลบ/กู้คืนได้; staff/anon ทำไม่ได้
- การแก้ตัวเลือกจานหนึ่งไม่เปลี่ยนจานอื่น; ชื่อ/ราคาในบิลเก่าไม่เปลี่ยน
- Retry หลังคำตอบหายไม่สร้างเมนู/รายการซ้ำหรือเรียงซ้ำ; การแก้จากสองเครื่องไม่ทับกันเงียบ ๆ
- กระเพราเพิ่มไข่ดาวคิดเพิ่ม 1,000 สตางค์ต่อจาน และเอาออกได้
- ไอศกรีมเล็ก 3/ใหญ่ 4 ผ่านทั้ง UI และ SQL; เกินจำนวนต้องถูกปฏิเสธ; ถั่วลิสงไม่กินโควตา และคำว่าไม่ใส่ถั่วลิสงถึงครัว
- ข้อความที่ตั้งค่าแสดงตรงกันใน preview/หน้าลูกค้า/POS; ค่าเริ่มต้นและเมนูเก่ายังอ่านได้
- Browser tests ที่ความกว้าง iPhone เล็ก/ใหญ่ ไม่มีแนวนอนล้นหรือปุ่มถูกแถบล่างบัง; ไม่อ้างว่าเป็นการทดสอบบน iPhone จริง
- รัน tests ที่เพิ่มและ regression เดิม, `pnpm check`, full browser suite, regenerate HTML, review, commits ขนาดเล็ก และอัปเดต README/HANDOFF
- ก่อน deploy ตรวจ migration history และข้อมูลปัจจุบัน ใช้เฉพาะ migration ใหม่ที่ตรวจแล้ว พร้อมปรับรายการที่ขอสามเมนู ห้ามล้างบิล รับเงินทดสอบ หรือเปลี่ยน QR บน production
- Deploy ฐานข้อมูล/API/frontend ตามลำดับที่เข้ากันได้ แล้วตรวจ public menu และ asset จริง งานทดลองรับออเดอร์ใช้ข้อมูลแยกจากร้านจริง
